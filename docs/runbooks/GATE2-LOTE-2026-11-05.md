## 3. Cómo verificar cada una

- **Deploy:** estado READY en Vercel y el dominio de producción respondiendo `/admin` (login).
- **Historial de Prisma** (Neon → SQL Editor, sólo lectura):
  ```sql
  SELECT migration_name, finished_at, rolled_back_at
  FROM _prisma_migrations ORDER BY started_at DESC LIMIT 5;
  ```
  La del PR con `finished_at` no nulo y `rolled_back_at` nulo.
- **RLS de las tablas nuevas:**
  ```sql
  SELECT c.relname, c.relrowsecurity, count(p.*) AS policies
  FROM pg_class c LEFT JOIN pg_policies p ON p.tablename = c.relname
  WHERE c.relname IN ('ProyectoRendicion','ProyectoAnticipo','ProyectoPinIngreso','CuentaContable','Ejercicio',
    'Asiento','AsientoLinea','ObligacionFiscal','VencimientoFiscal','ServiceDetail','ServiceFoto','UserPermissionOverride')
  GROUP BY c.relname, c.relrowsecurity ORDER BY 1;
  ```
  Cada tabla ya creada: `relrowsecurity = true`, `policies = 1`.
- **Funcional (clic por clic, 1 minuto):** PR1 → MIA: Proyectos → un proyecto → sección Rendiciones carga.
  PR2 → Contabilidad: plan de cuentas abre sin el aviso «falta aplicar la migración». PR3 → CH: Catálogo → un
  servicio → ficha completa guarda. PR4 → Usuarios → «Qué puede hacer cada persona» abre. PR5 → CH: Agenda y cobro
  del día como siempre (interruptor apagado = sin cambios).

## 4. Si algo falla

- **El build frena antes de migrar** (lote, conexión, árbitros): no se tocó nada; producción sigue con el código
  anterior. Leer el mensaje del log, corregir en un PR, volver a mergear.
- **Falla `migrate deploy`:** el build frena y producción sigue con el código anterior. Prisma **no** envuelve la
  migración en una transacción: puede quedar aplicada a medias, y `_prisma_migrations` la marca fallida y
  **bloquea los deploys siguientes (P3009)**. Arreglo (Gate 2, el dueño): mirar qué objetos quedaron creados,
  borrarlos (son todos nuevos), `npx prisma migrate resolve --rolled-back <nombre>` con la cadena de migración,
  corregir y reintentar. Si no está claro qué quedó, restaurar desde el respaldo (abajo).
- **Deploy READY pero algo anda mal en la app:** Vercel → Deployments → el anterior → **Instant Rollback**. Las
  migraciones son aditivas: el código anterior funciona con las tablas/columnas nuevas, no hace falta tocar la base.
- **Volver la base atrás** (último recurso, destructivo, sólo con orden del dueño): restaurar desde el branch
  `pre-lote-2026-11-05` (Neon → Branches → Restore). Se pierde lo escrito después del respaldo. Alternativa
  quirúrgica: borrar los objetos de la migración (tablas nuevas, columnas nuevas) y
  `DELETE FROM _prisma_migrations WHERE migration_name = '<nombre>'`; hacerlo **después** del Instant Rollback del código.

## 5. Riesgos conocidos

- **PR1 — schema-ahead en la caja.** Las columnas nuevas de `CashMovement` y `ProyectoLiquidacion` entran en el
  `select` por defecto de Prisma: el código de PR1 **no** tolera que falten (P2022 en toda lectura de caja). Está
  cubierto porque el build migra antes de publicar y frena si no pudo. No publicar PR1 por otro camino (redeploy
  manual sin la variable, preview apuntando a prod). Las tablas nuevas sí se toleran (`rendiciones-core.ts:31`).
- **PR2–PR4 toleran la ausencia:** `contabilidad/repo.ts:59-62`, `servicios/ficha.server.ts:13-16`,
  `permisos-overrides.ts:14,22` y `usuarios/matriz.server.ts:20` (P2021/P2022 → camino de hoy).

  `20260925120000_lanzamiento_base`. No la toca ningún PR.
